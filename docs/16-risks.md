## 還沒驗證的

依「出錯的話影響多大」排序。這一節是交接時的原文；現在的狀態看上一節。每一項都寫了在哪個階段確認、不成立時怎麼辦。

### 1. 真實電影上的人聲偵測與自動對齊

**現況**：所有對齊的數字都來自合成語音加上很輕的底噪。真實電影有配樂、音效、多人同時講話、長時間沒有對白。

**風險**：人聲偵測把配樂算成人聲，或漏掉輕聲的對白；分數的絕對值和門檻不同；自動對齊在某些片上找錯位置。這是整個產品最核心的功能。

**確認**：階段 0 第 6 項，用 Blender 的開放電影。

**不成立時**：
- 手動工具（對齊點、位移、吸附、分段）不依賴偵測品質，仍然可以把字幕對好，只是比較費工。產品仍然成立。
- ffsubsync 有其他偵測方式（`--vad silero`、`fused`，需要另外裝 torch，映像檔會大很多；以及用 whisper 轉錄，需要 ffmpeg 8 和模型檔）。先量，再決定值不值得。
- 兩種方法不一致時介面已經會提醒使用者多聽幾句。

### 2. 從部署的機器連到各個來源

**現況**：來源的行為是從一般的瀏覽器看到的。沒有從伺服器端大量請求過，沒有下載過任何字幕壓縮檔的內容，射手網、TMDB、SubDL 因為沒有金鑰完全沒有實際呼叫過。

**風險**：某個來源對非瀏覽器的請求、對某些 IP 範圍、或對頻率有限制；回應的欄位和文件有出入；壓縮檔的格式不是預期的。

**確認**：階段 0 第 4 項；階段 5 的手動驗收。

**不成立時**：那個來源依 D27 停用或改成協助式。JustSubtitles 有 SubDL 官方 API 當備援。上傳永遠可用。

### 3. 映像檔沒有實際建置過

**現況**：`deploy/Dockerfile.example` 和 `Caddyfile.example` 是照文件寫的，沒有跑過（準備環境連不到 Docker Hub，也沒有 Caddy）。compose 檔只驗證了語法。`.dockerignore` 也沒有實際驗證過。

**風險**：套件名稱、建置步驟、Caddy 的指令寫法有錯。另外，Dockerfile 範例用的基底映像檔帶的 ffmpeg 很可能比 6.1.1 新，而這份規格裡「完全相同」的比對（分析結果對 `fixtures/data.json`）是在 6.1.1 上做的；版本不同時可能有幾個影格的出入，怎麼處理寫在階段 0 第 2 項。

**確認**：階段 0 第 1 項。這應該是第一件做的事。

### 4. RAR 解壓縮

**現況**：中文字幕站大量使用 RAR。Dockerfile 範例裝的是 `libarchive-tools`（`bsdtar`），它宣稱支援 RAR 和 RAR5 的讀取，但沒有測過，準備環境裡也沒有工具能產生 RAR 測試檔。

**確認**：階段 0 第 3 項。

**不成立時**：改用其他能解 RAR 的工具（注意授權條款）；或者第一版不支援 RAR，上傳時請使用者先解開。射手網的 API 提供壓縮檔內個別檔案的下載網址，所以它不受影響。

### 5. ARM 的機器

**現況**：全部在 x86-64 上驗證。很多 NAS 是 ARM。

**風險**：WebTorrent 的原生模組（`utp-native`、`node-datachannel`）和 ffsubsync 的相依套件（`webrtcvad`）在 ARM64 上沒有預先編譯好的版本時，要在映像檔裡裝編譯工具，或關掉 uTP。

**確認**：階段 0，如果 Brian 的機器是 ARM。

### 6. 目標機器的效能

**現況**：耗時是在 2 核心的沙盒量的。對齊核心在 1,500 句上的耗時（約 3 秒）是估計的，沒有實測。

**風險**：NAS 的 CPU 可能更慢。2160p HEVC 轉預覽檔可能比即時還慢，一部片要好幾個小時。

**影響**：只影響預覽影片多久能用。只有聲音的模式幾分鐘內就能用，同步和匯出不受影響。

**確認**：階段 0 第 5 到 6 項、階段 4。

### 7. 瀏覽器直接播放 YTS 的檔案

**現況**：沒有拿真的 YTS 檔案在瀏覽器裡試過。假設 H.264 8-bit 加 AAC 的 MP4 可以直接播（包含 5.1 聲道），假設 `moov` 在檔尾時靠 Range 請求也能播。

**確認**：階段 0 第 7 項用自己做的類似檔案；Brian 實際使用時才會遇到真的檔案。

**不成立時**：那一類檔案也走預覽檔。判定規則集中在一個函式裡，好改。

### 8. WebTorrent 在真實環境的長時間表現

**現況**：只驗證過本機兩個用戶端互傳一個 24 MB 的檔案。

**風險**：Docker bridge 網路下的 DHT 和 uTP；幾 GB 的種子的記憶體用量；跑好幾天的穩定性；冷門種子的可用性。

**確認**：階段 0 第 5 項、階段 3；之後在實際使用中觀察。

**不成立時**：`torrent` 是獨立的程式，只透過資料庫和其他部分溝通。真的不行時可以把它換成別的下載程式的轉接層，其他部分不用動。這會違反 D4，要 Brian 同意。

### 11. 多個連線同時進來時的資料庫行為

**現況**：`storage_admit`（空間檢查）和 `provider_take_slot`（請求排隊）都在嵌入式的 PostgreSQL 上測過，但那是單一連線，測不到「兩個連線同時呼叫」。它們靠的是 advisory lock 和列鎖，在預設的隔離層級（READ COMMITTED）下理論上正確。

**確認**：階段 3 的「兩個下載同時搶最後一點空間」和階段 5 的「兩個程式同時對同一個來源發請求」這兩個測試，就是用真的 PostgreSQL 和多個連線來驗證它們。

### 12. 這一版規格裡沒有原型可以對照的流程

背景工作的認領與對帳、失敗後自動再試一次、刪除不等工作（工作自己停下來並收掉自己的產物）、上傳的檔案先變成一條候選、對外查詢做成工作：這些是把規格寫完整時補上的設計，邏輯上互相對過，但沒有任何一段實際跑過。實作時如果發現更簡單而行為相同的做法，可以提出來（它們不屬於「指定」或「代決」的決定）。

### 13. 相依套件的安全通報

2026-10-05 對 `webtorrent` 3.0.21 跑 `npm audit`，回報 4 個高風險，源頭都是同一個：`ip` 這個套件（GHSA-2p57-rm9w-gvfp，`isPublic` 對某些位址判斷錯誤），經由 `bittorrent-tracker` 和 `torrent-discovery` 被帶進來。`npm audit` 建議的「修正」是降到很舊的 webtorrent，不可行。

這份規格沒有評估它在這個用途下實際的影響。要做的事：

- 我們自己擋內部位址的程式**不要用 `ip` 這個套件**（[12-auth.md](12-auth.md)）。
- 階段 0 看一次現況（webtorrent 有沒有新版、那個通報有沒有修正版）。
- 階段 9 的相依套件檢查要對這一項寫出明確的結論：升級、替換、或說明為什麼在這裡不構成問題。

### 14. 分數的門檻

70% / 55%（全片）和 50% / 25%（單句）來自原型在合成素材上的觀察。正確字幕在合成素材上是 80%（字幕停留較久）到 95%（字幕等於發聲區間）。真實電影上的分布不知道。階段 0 第 6 項量過之後調整。

## 設計上已知的限制

不是問題，是選擇。使用者可能會問。

| 限制 | 原因 |
| --- | --- |
| JustSubtitles 每種語言最多 30 筆 | 它的介面就是這樣。熱門片的英文字幕會不完整；YIFY Subtitles 可以補 |
| 自動對齊找不到落差超過 60 秒的情況 | 搜尋範圍。使用者放兩個對齊點就能解決 |
| 對齊核心只找一個斷點 | 兩個以上的斷點靠 ffsubsync 的分段模式，或手動分段 |
| ASS 的樣式和特效會被拿掉 | D34 |
| 圖形字幕（VobSub、PGS）不支援 | 不是文字，沒辦法同步 |
| 字幕和同步結果是共用的，不能每個人各有一份 | 「有人對好了，其他人直接能用」比較重要。要不同版本可以加入另一條字幕 |
| 調低同時下載數不會暫停正在跑的 | 避免做到一半被打斷 |
| 重設密碼要找管理員 | 系統不寄信 |
| 不能用中文片名搜尋 | YTS 只認英文片名。中文片名只是顯示用的（有 TMDB 金鑰、而且有人替那部片搜尋過字幕之後才有） |
| 管理員不能直接操作別人的片 | 權限只看是不是持有人。管理員先加入片庫，或用強制刪除 |
| 匯出檔佔一份和原檔一樣大的空間 | 不重新編碼的代價。下載後刪掉就釋出 |

## 法律

不是法律意見。YTS 上的內容大多沒有權利人的授權；BitTorrent 下載時也在上傳。在大多數地區這樣使用有法律風險，由架設和使用的人承擔。這份規格在技術上做了幾件降低意外的事（只接受 YTS 的 hash、預設下載完就停止上傳、不對外開放註冊），但它們不改變上面這件事。

開發和測試全程不需要、也不應該下載有版權的影片。唯一會碰到真實字幕的是兩次手動的來源確認，每個來源下載一兩個壓縮檔看格式，看完就刪（D29）。
